# CodeMastery — UI/UX Design Specification

This file is the single UI/UX specification for the CodeMastery frontend. It
defines the visual system (in a light and a dark colour scheme, with a
system-matched preference), the information architecture, the user flows, the
screen specifications and the implementation handoff that Claude Code, Codex or
a human engineer must follow when building the frontend. It is a design
document: it does not approve APIs, routes, dependencies, files, permissions or
backend behavior. Where a screen consumes data, this file names the approved
contract that supplies it and designs only what that contract returns.

### Status vocabulary

Every screen, flow and integration in this file carries **two independent
labels**. Contract authority says whether the data and behavior a screen needs
are decided; delivery says what exists on the audited `main`. Neither label
implies the other: an approved contract is not an implementation, and a built
preview is not an approved contract.

**Contract authority** (uses the project's existing dispositions; see
[`docs/decisions/README.md`](docs/decisions/README.md#approval-status-labels)):

| Label | Meaning |
| --- | --- |
| **Approved** | Every operation and rule the screen consumes has an effective `LEADER_APPROVED`, `DELEGATED_APPROVED` or Leader-authorized record. The record is named on the screen. Approval is not implementation authorization. |
| **Partially approved** | Some consumed data or behavior is approved; the rest is missing, proposed or deferred. The screen designs only the approved part and lists the gap. |
| **Proposed** | Needs a decision that no effective record grants (`PROPOSED_NOT_EFFECTIVE`, `PENDING_*`). Not buildable as designed. |
| **Deferred** / **Blocked** | Not decided (`DEFERRED`, `BLOCKED_OR_UNRESOLVED`); the dependency is named. |
| **Superseded** | Replaced by a later effective record within its stated scope; kept only as history. |
| **No contract needed** | Pure presentation (for example the theme preference or the design preview) that consumes no governed API, permission or storage policy. |

**Delivery** (state of `main` at `65d14ca`):

| Label | Meaning |
| --- | --- |
| **Live** | Routed in the production app and consuming the approved API. |
| **Preview only** | Built as presentation components and shown only inside `/preview` with sample data. The preview may lag this file; [Known source discrepancies](#known-source-discrepancies-reported-not-resolved-here) lists where. |
| **Not built** | Specified here; no frontend code exists. |
| **Unmerged** | Exists only on an open branch or PR; not on `main`. |
| **Specified (r8)** / **Specified (r9)** | Introduced by that revision (for example the dark scheme in r8, the global Theme control in r9); no code exists yet. |

**Design decision** remains a third, separate notion: a choice made in this file
under the design delegation. It is binding for implementation unless a later
Leader-approved revision supersedes it, and it never substitutes for a
contract. The r7 labels map as follows: *Implemented* → Approved + Live;
*Preview* → (contract as stated) + Preview only; *Contract Pending* → now
Approved, Partially approved or Deferred per screen; *Proposed* and *Blocked*
keep their meaning. Route paths come from CT16.routes
(`CT16-ROUTES-2026-11-08-r1`); an approved path is registered in production only
under its activation rule (see [Sitemap](#sitemap)).

## Overview

**Creative North Star: "The Lit Path"**

CodeMastery shows a beginner programmer where they are, what they already know,
and the next sensible step, without hiding the course everyone shares. The
interface is a dark frame around a quiet working canvas. The frame is the
product's constant: navigation, identity and focus live in it, and it is the
darkest layer in every colour scheme. The canvas is where learning happens:
large, calm tiles on an even ground, connected by the dashed path line that runs
through lessons and through the skill graph. In the light scheme the canvas is
bright; in the dark scheme it dims to graphite but stays visibly lifted from the
frame, so the path still reads as lit. The path line comes from the logo, whose
hexagonal "C" holds three connected skill nodes. Colour is semantic: the pastel
families mean the four mastery states, the adaptive guidance and feedback,
never decoration, and each family keeps its meaning in both schemes.

The product is used by first-year university students in lecture halls,
libraries and dorm rooms, mostly on laptops in daylight and on phones between
classes, and increasingly at night during long study sessions, where the dark
scheme reduces glare. It is also used by instructors at a desk authoring
content and grading, and by an administrator handling users and reports. The
design therefore works in **Operate** mode for every workspace screen:
familiarity, legibility and state clarity outrank expression. Character comes
from precise details: the frame, the canvas reach, the path line, the type and
the mastery palette.

**Design principles**

1. **Next step first.** Every learner screen answers "what should I do now?" before it shows history or totals.
2. **Four kinds of truth, never blended.** Lesson completion, course progress, assessment scores and skill mastery are different facts. Each has its own component, wording and colour, and none stands in for another (see [Domain Presentation Rules](#domain-presentation-rules)).
3. **Explain every adaptation.** A recommendation always shows its type, its target and the reason supplied by the backend, verbatim. The canonical course order stays visible next to it.
4. **Guide, never lock.** A prerequisite gap produces a warning and a link to the evidence, never a lock icon or a disabled lesson.
5. **Honest data.** Real screens show decoded API data, including empty, unavailable and forbidden states. No placeholder numbers, invented charts, fake avatars or demo values outside `/preview`, and no figure the approved API does not return. The preview carries no visual "Sample data" label (Leader decision, 7 November 2026, [S26](#s26-design-preview)); its index subtitle says the screens use sample data.
6. **Earned familiarity.** Standard controls, standard navigation, standard tables. The frame and path line carry the identity, so controls stay ordinary.
7. **Accessible by construction.** Keyboard paths, visible focus, text labels for every state, reflow at 320 px and verified contrast in both colour schemes are part of every component specification.
8. **Two schemes, one identity.** The dark scheme is designed, not inverted: the same hierarchy (frame → canvas → tiles → raised surfaces), the same semantic families, the same type and shapes. Only token values change between schemes; components never branch on the scheme.

**Key Characteristics**

- Ink frame (`ink-950`) with the top bar and a canvas that rises into the active navigation item ("the canvas reach"), identical in both schemes.
- Even canvas (`canvas-100` light, `graphite-900` dark) with borderless tiles at 24 px radius.
- A contextual aside (`fill-150` light, `graphite-850` dark) carrying stacked, colour-coded guidance entries.
- A dashed path line linking ordered lessons and prerequisite skills.
- Pill-shaped buttons, filters and status chips; 44 px circular icon actions; neutral outlined circles for opening a tile and a primary circle only for Resume/Continue; neutral outlined secondary buttons.
- One UI family (Google Sans Flex) in a fixed product scale with large medium-weight titles; JetBrains Mono for code; Poppins ExtraBold only in the wordmark.
- Brand blue from the logo for interaction (links, focus, selection, progress); a high-contrast neutral fill for primary buttons (graphite on light grounds, mist on dark grounds).
- Identity blue (solid `brand-700`) for the signed-in account avatar only; no gradient fills on UI surfaces (the logo artwork and the skeleton shimmer are the only gradients).
- Course marks: one neutral container for every course, holding the official full-colour logo of the course's language or a code glyph.

### Reference Analysis

The primary reference image (3228 × 2638 PNG still) was opened and inspected
directly in a headless browser on 6 November 2026. Colours below were sampled
from its pixels. The shot also contains an MP4, which was **not** reviewed. The
typeface was identified by eye as a Gilroy-style geometric grotesque; this was
not confirmed against metadata.

**Decomposition**

| Aspect | What the reference does |
| --- | --- |
| Composition | A device-like frame: pure black (`#000000`) border and top bar, a rounded light canvas inset with roughly 8 px of black showing at the sides and bottom. Two zones: a main work area (about 70%) and a right "My Events" column (about 30%) on a slightly darker panel (`#EFEFEF`). |
| Top bar | Wordmark left; centred icon navigation in which only the active item ("Learning Plan") shows its label; the canvas edge rises in a small rounded hump under the active item; user avatar, name, email and chevron on the right. |
| Main area | Large page title with search pill top-right; a left vertical rail of circular view toggles (active toggle is a black circle); a two-column zig-zag of lesson tiles joined by a green dashed connector with dots (`#5DB951`); a stat trio (Total / Completed / Upcoming) whose third tile is a dashed outline. |
| Tiles | White (`#FFFFFF`) on `#F6F6F6`, no border, no visible shadow, roughly 28 px radius. Title about 26 px medium weight, two-line description in grey (`#535353`), footer with a status pill left and circular actions right (grey `#EFEFEF` circles, black confirm circle). A circular badge overlaps the top-right corner. |
| Aside | Stacked entries tinted sky (`#DFF8FB`), lilac (`#F0D0FB`), butter (`#FBE8B3`) and mint (`#CDFAD2`), each with a header row (icon, type, date) and a lighter inner panel (`#EDFBFD`, `#F5E1FC`, `#FDF0CE`). A white pill holds the entry action ("Start at 12:30"). A dashed empty slot ends the stack. |
| Typography | One geometric sans. Page titles about 44 px, tile titles about 26 px, body about 16 px, stat numerals about 40 px. Medium-to-semibold weights; no light weights; tight tracking on display sizes. |
| Data display | Counts only (26 / 2 / 23); state shown by pill text plus tint. No charts or tables. |
| Ornament | Emoji beside titles and in pills, 3D cartoon avatars, two tilted cards, a floating colourful tool dock, music-note doodles. |

**Strengths to keep.** Very clear two-level hierarchy (page title, tile title);
generous and consistent spacing; a frame that makes the canvas feel like a
working surface; a path metaphor that matches mastery learning; colour used in
families rather than as scattered accents; few, large, confident controls.

**Weaknesses to correct.** Icon-only navigation hides destinations; secondary
grey text and pastel tiles are near contrast limits; emoji and tilted cards are
presentation-shot theatrics that break in a working product; lock icons on
upcoming lessons imply hard blocking, which CodeMastery forbids; the stat trio
and pills carry no interaction states, focus treatment or error states; there
is no table, form or dense-data language at all; there is no dark scheme.

**Adopt, adapt, reject**

| Reference element | Decision for CodeMastery |
| --- | --- |
| Black frame + top bar + inset rounded canvas | **Adopt.** Ink `#0A0B0F` (slightly cool to sit with the logo blue). In the dark scheme the frame keeps this value and stays the darkest layer. |
| Canvas hump under the active nav item | **Adopt** as the signature "canvas reach", always paired with `aria-current` and a white label. |
| Icon-only nav with one labelled item | **Adapt.** All items labelled at ≥ 1200 px; at 900–1199 px only non-active items collapse to icons with tooltips and accessible names. |
| Page title + search pill on one row | **Adopt.** |
| Left circular view rail | **Adapt** into the View Rail used only where one dataset has several views (Mastery Map graph/list, course path/outline). |
| White borderless tiles, ~28 px radius | **Adopt** at 24 px (`rounded.lg`). |
| Zig-zag tiles with dashed connector | **Adapt** into the Path Spine: one column of lesson tiles with the dashed line in the left gutter. Zig-zag is rejected; it breaks reading order and reflow. |
| Status pill + circular actions in tile footer | **Adopt.** |
| Black check circle | **Adapt** into the primary circular action ("Open lesson"); lesson completion lives inside the lesson. |
| Corner badge on tile | **Adapt** to adaptive markers (Recommended, Remedial, Prerequisite gap). Always duplicated by a text tag. |
| Lock icons on upcoming items | **Reject.** Contradicts the no-hard-block rule. |
| Stat trio with dashed third tile | **Adopt** only for real counts. The dashed outline means "not yet" (Remaining, Unknown). |
| Tinted aside entries with inner panel and white pill action | **Adopt** as the Guidance Stack. Tints are semantic. |
| Dashed empty slot | **Adopt** for empty states and the file drop zone. |
| Geometric sans, medium titles | **Adopt** with Google Sans Flex (openly licensed; see Typography). |
| Emoji, 3D avatars, doodles, tilted cards, tool dock | **Reject.** |
| Avatar + name + email in top bar | **Adapt** to monogram + display name + role. Email must not be shown (CT16-PROFILE P2). |

**Fidelity contract.** Screens marked *High fidelity* in the
[page inventory](#page-inventory) must be recognisably in the reference's visual
language at about 90%: frame and reach, canvas and aside colours, tile radius and
padding, title scale, pill and circle controls, path line and stat trio. The
figure measures how closely these screens follow the reference's visual language
and design characteristics. It is not a target for reproducing the reference:
its composition, screens, artwork, illustrations, avatars, copy and identity are
not copied, and every CodeMastery screen is composed from its own content and
tasks. The figure applies to the light scheme; the dark scheme preserves the same
structure and proportions with its own values. Screens marked *Adapted* use the
same tokens with a task-specific composition. Screens marked *Specialized* (quiz
attempt, editors, admin tables, auth) share tokens and components but have their
own structure; forcing the dashboard shape onto them would harm the task. This
matches the course requirement to address a learning need "rather than merely
cloning the interface of an existing platform".

### Anti-patterns

- Same-size cards as page scaffolding; cards inside cards; KPI hero rows with invented trends.
- Gradient text, gradient fills, glass blur, glowing halos, decorative purple-blue gradients.
- Emoji or Unicode symbols as icons. Icons are drawn SVG in one stroke style.
- Eyebrow or kicker labels above headings, and section numbers.
- Coloured `border-left` stripes on alerts, list items, block quotes or tiles.
- Lock icons or disabled states for prerequisite gaps.
- "Mastery %", progress rings or confidence numbers. No numeric mastery exists.
- Spinners in the middle of content. Use skeletons.
- Modals for tasks that do not need interruption.
- Placeholder copy ("Lorem ipsum", "No data available") and fabricated demo values in connected screens.
- **Dark-scheme anti-patterns:** colour inversion or CSS `filter: invert()`; pure black (`#000000`) canvases; saturated "neon" accents or glows; light pastel tints on dark grounds; graphite primary buttons on graphite grounds; shadows used as the only boundary of a floating surface; a white flash before the stored scheme applies.

## Colors

A restrained ink-and-canvas neutral system, one brand blue for interaction, and
five pastel families with fixed semantic jobs, specified for two colour schemes.
Every raw value is in the frontmatter. Contrast ratios below were computed from
the hex values with the WCAG 2.x relative-luminance formula on 18 November 2026
(light pairs re-verified, dark pairs new), not measured in a rendered browser.

### Colour architecture

Colour is specified in three layers. Components consume only the second and
third layers, so the same component renders correctly in both schemes.

| Layer | What it is | Where it lives |
| --- | --- | --- |
| **Raw palette** | Named hex values with no meaning of their own: the existing light palette (`ink-*`, `canvas-100`, `fill-150`, `surface`, `brand-*`, the pastel families, `data-*`) and the dark palette added in r8 (`graphite-*`, `mist-*`, `brand-200/300/800/900`, the `-300/-900/-950` family steps, `rose-500`, `data-*-dark`) | Frontmatter `colors`; `theme.ts` `color` |
| **Semantic roles** | Scheme-independent names (`bg.canvas`, `text.secondary`, `accent.link` …), each mapped to one raw value per scheme | [Semantic role tokens](#semantic-role-tokens); the MUI palette and CSS variables of each scheme |
| **Component tokens** | A component's use of roles (`button-primary`, `tile`, `tag-mastery-weak` …); the frontmatter lists the light entry and a `-dark` entry where the values differ | Frontmatter `components`; MUI component overrides |

Existing raw names keep their values, so nothing in the light scheme moves. The
role names are new vocabulary for implementation; where an r7 rule names a raw
value (for example "`ink-600` text"), read it as the role in the
[name mapping](#token-name-mapping) and apply that role's value for the active
scheme.

a soft inner layer. Text on a tint is `text.primary`; secondary text on a tint is
`text.strong-secondary`. In the dark scheme the tint is a deep, low-chroma
container and the soft layer is darker than the tint, so inner panels recede
the same way they do in light.

### Named Rules

**The Semantic Pastel Rule.** A tint always means its family's job, in both
schemes. If a region is tinted, a reader can name why. Decorative tinting is
forbidden.

**The Two-Blues Rule.** The neutral primary fill is for doing (primary buttons,
primary circles): graphite on light grounds, mist on dark grounds. Logo Blue is
for where you are and what is selected (links, focus, selection, progress). A
primary button is never blue and a link is never neutral. Identity blue
(`brand-700`) on the account avatar names the user; it is not a third
interactive colour.

**The Never-Alone Rule.** No state is communicated by colour alone. Every tinted
state carries a text label and a glyph (CT16-FINAL F2). This also makes every
state readable in forced-colours modes.

**The Role-Not-Value Rule (r8).** Themed components consume semantic roles, never
raw hex values or the light `color.*` constants. A component that would render a
light value in the dark scheme is a defect. The frame (`bg.frame`) and the
identity colours are the only values shared by both schemes by design.

## Themes

New in r8. CodeMastery offers three theme preferences. The **preference** is
what the person chose; the **effective scheme** is what renders. Components only
ever see the effective scheme.

| Preference | Effective scheme |
| --- | --- |
| **System** (default) | `dark` when the operating system reports `prefers-color-scheme: dark`; otherwise `light` (also when the browser reports no preference or cannot be queried) |
| **Light** | `light`, whatever the operating system reports |
| **Dark** | `dark`, whatever the operating system reports |

**Contract authority:** No contract needed. The preference is a client-side
device setting. It is not a user-profile field, is never sent to the backend and
needs no endpoint, migration or synchronisation. Any future server-side
preference would need its own contract. **Delivery:** Specified (r8; global placement r9).

### Theme selector

Every visitor, signed in or anonymous, can choose the theme from every page.
One control model, the **Theme control**, appears in every shell, and each shell
has exactly one placement, so no page shows two competing selectors (design
decision D9-1, which supersedes D8-3 at the Leader's instruction of 18 November
2026).

  renders while the ADR014 restore runs (when the sign-in actions are still

  reset it.
- **Contrast (on the frame):** `chrome-muted` glyph on `ink-950` 8.16:1;

  track 16.66:1; `focus-on-chrome` on `chrome-raised` 8.00:1.

### Persistence and precedence

1. **Storage.** The preference is stored in `localStorage` under the key
   `codemastery.theme` with exactly one of the values `system`, `light` or
   `dark`. It is the only value this feature stores; it is non-secret and
   contains no identity. (The key name follows the existing
   `codemastery.auth.pendingSignOut` convention; it is a design decision of
   this file, not a governed contract.)
2. **Default.** A missing, empty, unknown or unreadable value means System.
   An invalid value is ignored (and overwritten only when the person next
   chooses a theme).
3. **Precedence.** A valid stored value wins over the operating-system setting;
   System defers to the operating system.
4. **Device scope.** The preference belongs to the browser profile, not the
   account: a choice made as a visitor is kept when the person signs in, and a
   choice made while signed in is kept after signing out. Signing in, signing
   out, a session ending in another tab or a different account signing in never
   changes or clears it, and it applies to public and authenticated pages alike.
   No account, sign-in, endpoint or database field is involved.
5. **Storage unavailable** (private modes that throw, blocked storage, quota):
   the selection still applies for the life of the document and is kept in
   memory; nothing is shown as an error.

### Rendering, reloads and other tabs

- **First paint.** The effective scheme is applied to the root element (a
  `data-color-scheme="light|dark"` attribute plus the CSS `color-scheme`
  property) **before the first paint**, by a small synchronous script that runs
  before the application bundle and reads only the stored preference and
  `matchMedia('(prefers-color-scheme: dark)')`. The root `background-color` comes
  from CSS keyed to that attribute, so neither scheme flashes the other. The
  frame colour is the same in both schemes, so the brief pre-application moment
  (before the canvas renders) is already correct. The script must remain
  compatible with any future Content Security Policy (an external file or an
  allow-listed hash); no CSP exists on the audited `main`.
- **Navigation.** The scheme is application state, not page state: in-app
  navigation never re-evaluates or flashes it.
- **Reload.** Re-runs the first-paint step, so a reload shows the stored
  preference immediately; the ADR014 "Restoring your session…" state renders in
  the effective scheme.
- **System changes while open.** With the System preference, a change of the
  operating-system setting (manual or scheduled) is followed live through the
  `prefers-color-scheme` change event, without reload, and the System item's
  caption updates. With Light or Dark, operating-system changes are ignored.
- **Other tabs.** A selection in one tab is applied in every other open tab of
  the origin through the `storage` event, without reload. Where that event is
  unavailable, other tabs update on their next load.
- **Transition.** The switch is instantaneous: colour transitions are suspended
  for the switch so hundreds of elements do not animate, and nothing fades.
- **`theme-color`.** The browser UI colour stays `#0A0B0F` (the frame) in both
  schemes.

### Preview behavior

- `/preview` renders in the person's effective scheme on load (reading the
  stored preference is allowed; the preview never **writes** browser storage,
  an existing tested rule).
- Every previewed shell carries the Theme control in its production placement
  (top bar ≥ 900 px, drawer below, landing header, auth brand panel or header).
  In the preview a selection applies to the whole preview document **in memory
  only**: it does not write `codemastery.theme`, does not reach other tabs and is
  gone on reload. Until a preview-local selection is made, the preview follows
  the stored preference, including changes made in another tab. "Reset sample
  data" does not change the scheme.
- Screens rendered without a role shell keep their own placement: the landing
  and auth samples show their Theme button; the quiz attempt has none (as in
  production) and uses the scheme chosen elsewhere in the preview.
- The index's design reference shows each colour token in both schemes side by
  side (light value, dark value, role name), plus the semantic families,
  mastery tags and data fills in both schemes, so a reviewer can compare without
  switching. No preview chrome is added (S26).

## Typography

**UI Font:** Google Sans Flex 4.005 (Google Fonts v23, SIL Open Font License 1.1),
the one primary UI typeface. Self-hosted variable WOFF2 on the weight axis (1–1000;
400–700 used), subset like the Google Fonts API into Latin, Latin Extended and
Vietnamese files with `unicode-range`, `font-display: swap`, fallback
`ui-sans-serif, system-ui, -apple-system, 'Segoe UI', sans-serif`.
**Code Font:** JetBrains Mono 2.211 (SIL OFL 1.1), variable weight 100–800, the
same three subsets. It is the theme's `codeFontStack` and the only face for
`pre`, `code`, `kbd`, `samp`, code blocks, the code-snippet field and raw
identifiers.
**Brand Font:** Poppins ExtraBold 800 4.004 (SIL OFL 1.1), one Latin file
declared as the family "CodeMastery Wordmark" so no other text can match it. It
sets only the "CodeMastery" wordmark (see Brand and logo).

**Selection (7 November 2026).** The Leader ranked PP Neue Montreal 3, Suisse
Int'l, Google Sans Flex, Inter and Be Vietnam Pro for the UI. PP Neue Montreal 3
(Pangram Pangram) and Suisse Int'l (Swiss Typefaces) are commercial: the project
holds no web-embedding licence that covers distribution to every team member
and every visitor, so neither can be bundled. Google Sans Flex, the next in rank,
is openly licensed, has complete Vietnamese coverage (Đ/đ, ă, â, ê, ô, ơ, ư and
every tone-marked letter; verified against the shipped files), a continuous
weight axis and small files, so it was selected and the lower-ranked candidates
were not evaluated further or installed. Its subset omits `₫` (U+20AB), which the
product does not display.

**Character:** a contemporary humanist-geometric sans with open apertures, a
double-storey `a`, generous x-height and calm proportions; legible at 13 px, with
tabular figures for scores and timers. Figtree (the UI face from 6 to 7 November
2026) and Plus Jakarta Sans (the face before it) are retired. They are historical
only: no current file, token or rule uses them.

**In the dark scheme** sizes, weights and line heights are identical. No weight
is lowered to compensate for light-on-dark rendering, and no weight below 400 is
used anywhere, so text does not thin out on graphite.

### Named Rules

**The One Family Rule.** Google Sans Flex carries everything except code and
the wordmark. No other display face, no italic display, no uppercase tracked labels.

**The Wordmark Only Rule.** The brand face appears only in the "CodeMastery"
wordmark, never in headings, buttons or navigation.

**The Fixed Scale Rule.** Sizes are fixed rem steps that change only at the
600 px breakpoint. No `clamp()` or viewport units anywhere. One documented
exception: the top-bar lockup takes one more fixed step below 390 px (32 px mark)
so the narrowest bars never scroll; it is local to the lockup, not a global
breakpoint.

**The Monospace Is For Code Rule.** Monospace appears only for code, program
output inside Markdown code blocks and raw identifiers (audit codes, UUIDs on
the Profile page and in audit targets). Quiz prompts and options are plain text
in the UI face (see [S11](#s11-quiz-attempt)).

- **Frame.** `body` background is `bg.frame` in both schemes. The top bar is part of the frame and is sticky.
- **Canvas.** `bg.canvas`, `rounded.xl` corners, inset 8 px from the left, right and bottom frame edges at ≥ 600 px. Below 600 px the canvas runs edge to edge with 24 px top corners only. The document scrolls; the canvas is not an inner scroll container.
- **Canvas reach (concave curved bottom-edge indicator).** Under the active top-nav item the bar's lower edge bends up in one soft, symmetric bell, so the canvas appears to rise into the active tab. Geometry traced from the reference (shot 23956256, the hump under "Learning Plan"; width ≈ 6.2 × height): 88 × 14 px, long concave shoulders that leave the straight edge tangentially, an inflection near mid-height and a rounded convex crest centred on the item. Profile per half `y(u) = ((1 − cos πu) / 2)^1.2`, drawn in `AppHeader` (`canvasReachPath`) as a Catmull-Rom spline converted to cubic Béziers and mirrored exactly; not an underline, pill, dot or notch.
  - **Technique (7 November 2026):** nothing is painted. The bell path is a CSS mask layer (`REACH_MASK`, 88 × 15) subtracted from the header with `mask-composite: exclude` (`-webkit-mask-composite: xor`), so the bar's own ink is cut and the opening is transparent. The canvas begins 14 px under the bar (`margin-top: -14px`, `padding-top: 14px`), and its outline is a `clip-path` (`canvasOutlinePath`) whose visible top corners start exactly at the bar's bottom edge; the opening therefore shows the canvas itself, continuous with the canvas below, with no seam, overlap line or fill colour to match. Because nothing is painted, the technique works unchanged in the dark scheme. When the page scrolls under the sticky bar, whatever passes underneath (a tile, text) shows through the opening.
  - It is decorative (no element, nothing focusable), re-centres when the window, the labels or the web fonts move the item (`ResizeObserver` on the header, the bar and its slots, plus font loading), and the active item also has `aria-current="page"` and a white label. The header exposes `data-canvas-reach`, `data-reach-for` and `data-reach-x` for tests.
- **Main column.** Max content width 1440 px inside the canvas; horizontal padding 40 px (≥ 1200), 32 px (900–1199), 24 px (600–899), 16 px (< 600). Page top padding 40 px (≥ 900), 24 px below.
- **Aside panel.** On pages that have one, a right column inside the canvas, `bg.fill`, full canvas height, 360 px at 1200–1535 px and 400 px at ≥ 1536 px, with `rounded.xl` on its outer corners and no border. Below 1200 px the aside's content moves into the main column at the position each screen specifies.

## Elevation & Depth

Depth comes from **tonal layering**: frame → canvas → tiles, and canvas → aside
→ tinted entries. Surfaces at rest have no border and no shadow. Shadows appear
only for elements that float above the page or respond to a state.

### Shadow vocabulary

| Role | Light | Dark | Use |
| --- | --- | --- | --- |
| Hover lift | `0 6px 20px rgba(10, 11, 15, 0.08)` with `translateY(-2px)` | `0 6px 20px rgba(0, 0, 0, 0.40)` with `translateY(-2px)`; tile background `bg.hover` | Clickable tiles on hover (pointer devices only) |
| Control | `0 2px 8px rgba(10, 11, 15, 0.10)` | `0 2px 8px rgba(0, 0, 0, 0.45)` | The selected segment of a segmented control |
| Raised | `0 12px 32px rgba(10, 11, 15, 0.12)` | `0 12px 32px rgba(0, 0, 0, 0.55)` + 1 px `line.hairline` outline | Menus, popovers, selected graph node, side sheets, sticky lesson bar |
| Overlay | `0 24px 64px rgba(10, 11, 15, 0.20)` | `0 24px 64px rgba(0, 0, 0, 0.65)` + 1 px `line.hairline` outline | Dialogs, mobile drawer (the drawer, on ink, takes no outline) |
| Scrim | `rgba(10, 11, 15, 0.48)` | `rgba(0, 0, 0, 0.64)` | Behind dialogs and the drawer |

### Named Rules

**The Flat-At-Rest Rule.** A resting surface declares elevation once: by tone or
by shadow, never a 1 px border plus a soft shadow. Tables are surfaces on canvas
with hairline row separators and no outer border. In the dark scheme, floating
surfaces (Raised, Overlay) add a hairline outline because their shadow cannot be
seen against graphite; resting surfaces never do.

## Shapes

- Corner scale: `xs 8` (mastery and type tags), `sm 12` (tooltips, code blocks, inner panels of small entries, menu items), `md 16` (text fields, selects, inner panels of guidance entries, quiz options), `lg 24` (tiles, tables, aside entries, menus, side sheets), `xl 32` (canvas, aside panel, dialogs), `pill` (buttons, search, status pills, segmented controls, View Rail, timers).
- Circles: icon buttons (44 px), account avatar (40 px top bar, 64 px Profile), Q&A monograms (36 px), Path Spine nodes (20 px, 14 px not started, 10 px static), corner badges (40 px on tiles, 28 px on map nodes), quiz navigator (44 px).
- Course marks: 48 px squares at `rounded.md` (the radius scales with the mark).
- Dashed outlines: 1.5 px `line.strong`, 6 px dash / 6 px gap, `rounded.lg`. Reserved for "not yet" meanings (Unknown, Remaining, empty slot, drop zone).
- Path line: 2 px, 4 px dash / 6 px gap (`pathLine` in `theme.ts`), used by the Path Spine, prerequisite edges, the map legend and the auth brand path.

**The Pill-Is-An-Action-Or-A-State Rule.** Pills are reserved for things you can
press or for short states. A paragraph never sits in a pill.

A count read failure hides the badge silently; the button still works.
- **Anonymous utilities:** the Theme button, "Sign in" text button (white) and "Create account" on-chrome white small pill (40 px); below 900 px the Theme control and "Create account" move to the drawer footer. While a reload restores the session (ADR014), the sign-in actions render nothing, so they never flash; the Theme button stays.

Four ranks, one fill per rank. The roles live in `theme.ts` as `control`

| Rank | MUI usage | Rest (light / dark) | Hover (light / dark) | Use |
| --- | --- | --- | --- | --- |
| **Primary** | `variant="contained"` (default colour `ink`) | Graphite pill (`chrome-raised`), white label / mist pill (`mist-50`), ink label | `chrome-hover` / `surface` (white) | The one main action of a region: submit a form, start, save, enroll, confirm |
| **Secondary** | `variant="outlined"` | `control.secondary` pill with 1 px `line.hairline` border, `text.primary` label | `bg.hover` fill | Alternatives and supporting actions: cancel, refresh, "My courses" beside Enroll, error retry |
| **Tertiary** | `variant="text"` | No fill or border, `accent.link` label (12 px padding) | `accent.link-hover` + underline | Low-emphasis inline actions ("Skip and start from the beginning", "View result", alert actions); on tinted grounds it may take `text.primary` (`color="inherit"`) |

- **Shared states:** 48 px (40 px `size="small"`), label type, pill radius; pressed scale 0.98; focus 2 px `focus.ring` with 2 px offset (on the frame `focus-on-chrome`); disabled primary and destructive `control.disabled`, disabled secondary keeps its surface and border with `text.disabled`, disabled tertiary has no fill; busy submits keep their width and announce progress (`aria-busy` or a status line).
- **On the ink frame** (`color="onChrome"`): primary is a white pill with an ink label (hover `fill-150`); secondary is a graphite pill with a white label (hover `chrome-hover`). Used by the top-bar and landing "Create account", the landing hero and the quiz "Submit quiz". Identical in both schemes because the frame is.
- **Circular actions** (`CircleAction`, 44 px, 20 px icon, accessible name and tooltip): `ink` = primary circle (`control.primary`), `fill` = secondary outlined circle, `plain` = no surface. Overflow "More actions" buttons and the lesson bar's previous/next circles use the secondary surface.
- **Tile arrow** (`CircleAffordance`, decorative because the tile's title link covers the tile): `secondary` by default — `control.secondary` circle with hairline border and a `text.primary` arrow; it fills `bg.hover` while the tile is hovered. `primary` only for the one important next step: the Learner home "Continue learning" tile (play glyph) and the resume lesson on the course path.

An empty state that repeats the title row's action makes it secondary; an error block's "Try again" is secondary; a banner inside a page that already has a title-row primary uses a secondary action (placement "Start diagnostic").

Controls never use it: primary buttons, primary circles, the selected page number, the selected View Rail toggle and answered quiz-navigator circles use `control.primary`. Blue is not used for buttons; it stays with links, focus, selection and progress.

### File upload and download

The shared widget is `shared/components/FileUploadField.tsx` (CT37.widget,
ADR010 §13).

- **Upload:** one file. A dashed drop zone (`line.strong`, `rounded.lg`) with the upload glyph, "Choose a file or drop it here" and the requirement text from the contract: "PDF file" for lesson materials, "PDF or ZIP file" for assignment submissions. The size limit is **not** shown (the frontend receives no configuration). States: idle; drag-over (`bg.selected`); uploading (indeterminate linear progress, control disabled, cancellable through the request signal); accepted (mint row with the file name and the server time); rejected (rose message). Client checks (extension, non-empty) only improve feedback; the backend decides.
- **Unknown outcome:** after a network failure or a 500 the UI reloads the resource and shows its current file before offering another upload; there is no automatic retry.
- **Replacing a submission** requires a confirmation dialog naming the current file and its time ("Replace file? Your current file *report.pdf*, submitted 20 Nov, 14:05, will be replaced.") with the confirm button "Replace file".
- **Messages:** 400 field errors verbatim; 409 → "The deadline has passed." or "This submission has been graded and can no longer be replaced." (chosen from the reloaded state); 413 → "The file is larger than the allowed size."; other failures use the generic patterns.
- **Download:** a secondary button with the download glyph and the file name ("Download report.pdf") fetches the file through the shared transport and saves it under the server filename. No inline preview, iframe or new tab; nothing is persisted. Storage URLs and object keys never appear.

### Tables

- One `bg.surface` `rounded.lg` surface on canvas. Header row: caption 600 `text.secondary`, 48 px, no fill, sortable headers show an arrow glyph and `aria-sort` (only where the API orders by that column). Rows: 60 px min, body-small, hairline separators, hover `bg.hover`, selected `bg.selected` (text `text.primary`, links `accent.link-on-tint`, never `text.tertiary`).

### Feedback

- **Inline alert:** `rounded.md`, family tint, 20 px glyph in the family strong colour, title (label) and body in `text.primary`, optional actions on the right. No coloured left border. Used for page-level and form-level messages.
- **Tooltip:** `bg.inverse` with `text.inverse` caption, `rounded.sm`, 8 × 12 px padding, max 280 px, appears after 400 ms on hover and immediately on keyboard focus, dismissible with Escape. Tooltips repeat names; they never hold the only copy of information.
- **Toast:** `bg.inverse` pill at bottom centre, `text.inverse` body text, optional text action (`focus-on-chrome` in light, `brand-700` in dark), 6 s, pausable on hover/focus, announced politely. Only for background confirmations that do not belong next to a control.
- **Confirmation dialog:** see Dialogs. Destructive confirmations focus Cancel first (existing behavior).
- **Loading:** a visible `role="status"` line naming what is loading ("Loading your courses…"), followed by `skeleton` blocks shaped like the content with a 1.2 s shimmer (static with reduced motion). No spinner accompanies content loading; busy submit buttons keep their own inline indicator.
- **Empty state:** dashed slot with a 24 px glyph, a title that names the situation, one sentence that teaches the next step, and at most one action.
- **Error state:** a rose-tint block at `rounded.lg` with an alert glyph, a title that names the problem, one sentence of recovery, and a small secondary "Try again" button when a retry is possible. Field and form errors use the rose inline alert.
- **System state** (Page not found, Access denied, Restoring your session): centred block inside the shell, 64 px `bg.surface` circle with the glyph, page title, one sentence, actions.

### Dialogs, side sheets and menus

- **Dialog:** `bg.raised`, `rounded.xl`, 32 px padding, max 560 px, Overlay shadow, scrim. Title (item title), body, actions right-aligned (secondary then primary). Focus is trapped and returns to the trigger. Full-screen sheet below 600 px.
- **Side sheet:** right-anchored 480 px `bg.raised` panel for record detail in Manage pages (report detail, user detail); full-screen below 900 px.
- **Menu:** `bg.raised`, `rounded.lg`, Raised shadow, 44 px items, `bg.selected` for the focused item; `menuitemradio` items (Theme menu) show a trailing check when checked.

### Progress

Linear only: 8 px pill track `line.hairline`, fill `accent.progress`, with the
value in text beside it ("12 of 20 lessons · 60%", from CT22.progress
`completedLessons`, `totalLessons` and the floor `progressPercentage`). No
progress rings.

Quiz timer is a pill on the frame: white with ink text, clock glyph + `mm:ss` in
tabular figures, counting down to the server's `expiresAt`.
*Visual thresholds:* it turns butter when 20% of the time limit remains and rose
when one minute (or 10% of the limit, whichever is shorter) remains.
*Screen-reader announcements:* exactly one polite `role="status"` message at each
of those two changes — "N minutes left." (remaining minutes rounded up; "1 minute
left." for one) when it turns butter and "Less than a minute left." when it turns
rose — and nothing per second or per minute in between. These are presentation
thresholds, not quiz policy: admission is decided by the server (strictly before
`expiresAt`, ADR007 §9).

### Code and Markdown content

- **Code block** (`CodeBlock`): `bg.code` panel (dark adds the `line.code` hairline), `rounded.sm`, 20 px padding, JetBrains Mono 15 px in `text.code`, horizontal scroll, focusable; a 40 px copy button whose tooltip and status message change to "Copied"; optional caption below in caption type. Monochrome: there is no syntax highlighting, because CT37.markdown renders fenced code with `CodeBlock` and no highlighting dependency. A highlighting palette would need a dependency decision first.
- **Inline code:** `bg.fill` background, 4 px radius, `text.primary`.
- **Markdown** (CT37.markdown, `CT37-MARKDOWN-2026-11-08-r1`, [`docs/setup.md`](docs/setup.md#ct37markdown--ct37-markdown-2026-11-08-r1--delegated_approved)) renders `lessons.content_markdown` and text materials: body-reading in `text.primary`, 70ch measure, headings from `h2` at section-title and title sizes, 1.5 em paragraph spacing, links `accent.link`, tables in the table style without toolbar, block quotes as an indented `bg.fill` panel at `rounded.sm` (no coloured left border). CommonMark with tables and fenced code rendered as React elements; raw HTML is shown as literal text, never interpreted; only `https`/`http` URLs, root-relative paths (not `//…`) and `#` fragments become links, checked after decoding, and every other target is plain text; images render as links, not inline. The renderer library is a separate dependency decision.
- **External video** (CT37.embed, `CT37-EMBED-2026-11-09-r1`, ADR006 §6): only the canonical `https://www.youtube-nocookie.com/embed/{videoId}` is accepted and revalidated by the frontend. Before activation, a 16:9 `bg.fill` placeholder at `rounded.lg` shows the video material title, the play glyph and a keyboard-accessible secondary button "Load external video (YouTube)"; no iframe, thumbnail, script or request exists before activation. Activation creates the iframe (title = material title, no autoplay). Where the viewport cannot give the provider's 200 × 200 px minimum, the placeholder offers "Open video on YouTube" (external glyph, new tab, `noopener noreferrer`) instead. An unsupported stored URL renders "This video can't be shown." in `text.secondary`. Loading or playing a video never marks completion.
- **Plain-text content** (notification messages, Q&A posts, report reasons, assignment feedback, recommendation and practice reasons, quiz prompts and options): rendered as plain text with line breaks preserved; no Markdown, HTML or auto-linking.

### Mastery Map node and edge

- **Node:** `rounded.lg` 220 × 72 px, `bg.surface` (light) or `bg.raised` (dark), flat at rest with a 1 px inset `line.hairline`, Hover lift on hover; left 40 px state glyph circle in the state tint (dashed for Unknown); skill name (title, 2 lines max); state word (caption) under it. ### Charts (Administration and insights)

Built as semantic HTML/SVG with the existing stack; no chart dependency is added.
Horizontal bars sorted by value, value labels at bar ends in `text.primary`,
`accent.link` fill for single series, `data-*` fills plus hatch for mastery
distributions (100% stacked bars per skill, 2 px `bg.surface` gaps between

## Do's and Don'ts

### Do:

- **Do** keep the ink frame, canvas reach and canvas on every authenticated and public workspace page, in both schemes. The landing page (own ink header and hero), the auth split layout and the quiz attempt (Focus bar) are the deliberate exceptions.
- **Do** use exactly one `h1` per page and let it receive focus on route change.
- **Do** show the state word and glyph in every mastery, progress, membership and status indicator.
- **Do** use the Path Spine for anything with canonical order (lessons) and the dashed edge for prerequisites.
- **Do** put the reason text from the backend, verbatim, on every recommendation and recommended practice, with the mastery statement where ADR011 §9 requires it.
- **Do** use the neutral primary fill for the one primary action per region, neutral outlined buttons for alternatives, and Logo Blue for links, focus and selection.
- **Do** consume semantic roles, so every component works in light and dark without a branch.
- **Do** show skeletons shaped like the content while loading.
- **Do** keep tables in one surface with a toolbar above and pagination below.
- **Do** keep the Theme control reachable in every shell (top bar, drawer, landing header, auth panel), with exactly one placement per shell.
- **Do** keep all interface text in English, sentence case.

### Don't:

- **Don't** show lock icons, disabled lessons or blocking dialogs for prerequisite gaps.
- **Don't** show a mastery percentage, a confidence score, a threshold or a progress ring to learners.
- **Don't** call membership "Completed" a mastery outcome or show it on the Mastery Map.
- **Don't** show answer keys or correct options to learners; results show the learner's own selection and correctness only.
- **Don't** use emoji, Unicode symbols or third-party icon fonts as icons.
- **Don't** tint a region without a semantic reason, or give a UI surface a gradient fill (the logo artwork and the skeleton shimmer are the only gradients).
- **Don't** wrap a table, a form or a section heading in a tile.
- **Don't** show email, token data, account status or permissions in the account menu or Profile.
- **Don't** render numbers, names, titles, links or charts that the approved API did not return.
- **Don't** put `ink-500` text on `fill-150` or `brand-100`, `brand-600` text on `brand-100`, or `brand-400` text anywhere.
- **Don't** hard-code a light value (`color.*`, `#FFFFFF`) in a themed component, or invert colours to make a dark scheme.

## User Flows

Each flow lists its contract and delivery, the happy path, then the states that
must be designed. "→" means navigation; "⟳" means an in-place update. No flow
retries a mutation automatically (CT16, ADR014 §7); every retry is a deliberate
user action, and an uncertain outcome is resolved by reading the resource first.

### F1 Create account, sign in and recover access

*Contract:* Approved (CT01.core; ADR014; CT02 r1 and CT38-PASSWORD-RESET for
recovery). *Delivery:* account creation and sign-in Live; recovery Preview only.

1. Visitor → "Create account" → form (email, display name, password, confirm password) → submit.
2. Success: inline mint alert "Account created. Sign in to continue." with a "Sign in" button → Sign in (no auto-login). Nothing is passed to the sign-in page.
3. Sign in → success → the one-use `/profile` return when one was captured (CT16-PROFILE P1); otherwise a Learner lands on `/home`, an Instructor on `/teach` and an Administrator on `/admin` once those screens are routed, and both on `/courses` until then (CT16.routes). The refresh cookie set by the server is invisible to the UI.
4. **Recovery** (once FE06 is routed): the sign-in form shows the tertiary link "Forgot password?" → `/forgot-password`: one email field and "Send reset link" → the acknowledgement returned by the API, verbatim: "If an account matches, a password reset link will be sent." (identical for every input; no account enumeration), with "Back to sign in".
5. The email link opens `/reset-password#token=…`. The page reads the capability from the fragment into memory and replaces the history entry with `/reset-password` before any request; the token never appears in the DOM, a field, a query, storage or logs. Form: new password (with the live checklist) and confirm → "Reset password" (disabled while pending) → success shows the API message verbatim, "Password reset. Sign in with your new password.", plus "Other signed-in sessions on your account have been signed out." (ADR014 §6 revokes every session of the account), and a primary "Sign in". No session is created.

States: field errors on submit, then re-validated on blur for fields already in
error (focus the first invalid field or the error summary); the conflict returned
by the API for an existing email; the generic credential failure returned by the
API for wrong credentials and locked accounts alike (no account enumeration);
busy button; network failure with retry. Password rules appear as a checklist
under the field that updates while typing, using the exact approved predicates
and wording ("At least 15 Unicode characters, at most 72 UTF-8 bytes."; no
trimming). Recovery: an invalid, used or expired link (the API's generic 400) or
a reloaded page without a capability → "This reset link is invalid or has
expired." / "Request a new link from the sign-in page." / "Request a new link".
The reset page loads no third-party resource.

### F2 Session lifecycle

*Contract:* Approved (`AUTH-SESSION-2026-11-16-r1`, `CT16-SESSION-2026-11-16-r1`,
ADR014 §§6–7; supersedes the memory-only, reload-loses-session behavior of
CT16-r1/CT16.minimum within ADR014 §11). *Delivery:* Live.

- **Restore.** On every load the provider restores the session from the HttpOnly refresh cookie. While it runs, protected routes show the system state "Restoring your session…" (status line + block skeleton) instead of redirecting, the landing page waits with the same line, and the header shows no sign-in actions. A restored session continues on the page the person opened. A document opened at `/preview` never restores.
- **Renewal.** Silent: the access token is renewed shortly before it expires; the page, its data and its scroll position stay as they are. Transient network or server failures retry quietly until the token expires.
- **Other tabs.** Signing in or out in one tab applies to every tab of the origin without reload: another tab's sign-in is adopted; another tab's sign-out signs this tab out.
- **Sign out** (account menu): clears the session at once (offline too) and replaces to `/login` with no notice. The server revocation follows and is retried on a later load if it could not be confirmed; nothing about this is shown.
- **Session ended** without signing out in this tab (refresh refused, a 401 on the current session, sign-out in another tab, a password reset or account lock elsewhere): replace to `/login`, where a sky info alert (`role="status"`) says once: "Your session ended. Sign in again to continue." A wake-up that the cookie restores clears the notice.
- **Theme:** the effective scheme is applied before the restore starts and never changes with the session; a visitor's choice carries into the signed-in session.
- **Never shown:** token or cookie details, lifetimes, session counts, "remember me" or "sign out everywhere" (no such operation exists).

States: a 403 keeps the session (Access denied or the screen's own message);
network and 5xx responses are never treated as sign-out.

### F6 Take a quiz

*Contract:* Approved (CT04.start/submission/expiry/results, CT23, ADR011 §5
save-before-submit). *Delivery:* Preview only.

Assessments, a lesson or a recommended practice → quiz intro (kind, question
count, time limit, "The timer starts when you begin", previous
attempts) → "Start quiz" (or "Resume attempt" when an active attempt exists; the
timer is not reset) → attempt (Focus): navigate questions, answer, see the timer.
The full answer set is saved when the learner moves to another question or opens
the navigator, and always before submitting; a status line under the question
shows "Saving…", "All answers saved" or "Answers not saved. Try again." → "Submit
quiz" → confirmation "Submit quiz? You answered 8 of 10. Unanswered questions
score zero." → save, then submit → Result.

- **Save fails before submit** (or its outcome is unknown): the quiz is not submitted. The client re-reads the attempt and shows "We couldn't save your answers, so the quiz wasn't submitted. Your answers are still on this page." with "Try again"; if the server now holds different saved answers (another tab), the page shows the server's state and says so ("Answers saved from another window are shown.").
- **Submission fails** (500): the attempt stays active; "Something went wrong on our side. Your saved answers are kept. Try submitting again." Resubmitting is a deliberate action.
- **Time is up:** when the timer reaches the server's `expiresAt`, inputs lock and a status replaces the controls: "Time is up. Your last saved answers will be submitted automatically." with "View result". Late answers are never sent. If the result is not ready (409), "Your result isn't ready yet. Try again in a moment." — no polling.
- **Already submitted** (another tab or the scheduler): the submit returns the stored result → Result.

States: start failure; an overdue attempt still being finalized (409 on start:
"Your previous attempt is still being submitted. Try again in a moment.");
connectivity loss during the attempt (inline rose alert; the timer keeps
counting because expiry is fixed at start); leave guard on the exit button
("Leave the quiz? The timer keeps running. Your saved answers are kept."); a
hidden Quiz or Course (404) or left membership (403). The app uses a declarative
`BrowserRouter`, so in-app navigation blockers are not available; browser Back
and tab close are covered by the native `beforeunload` prompt, and returning to
an active attempt resumes it.

### F14 Access, errors and recovery

| Situation | Design |
| --- | --- |
| Reload or new tab with a session cookie | "Restoring your session…" until the restore finishes (F2); no redirect meanwhile |
| Anonymous on a protected route | Replace to `/login` (Live). The session-ended notice appears only per F2 |
| Wrong role | Access denied page inside the shell: title "You don't have access to this page", body "You're signed in as an Instructor. This page is for learners.", actions "Go to catalogue" and "Profile". Uses only the session role |
| Unknown URL, or a `†` path not yet routed | "Page not found" / "Check the address, or continue from the catalogue." / "Browse courses" |
| Hidden or missing course or descendant (concealed 404) | "Course not available" / "This course doesn't exist or isn't published." / "Back to catalogue"; Lessons, Quizzes and Assignments use the same pattern with their own noun |
| Forbidden resource inside a screen (403) | The screen's own message naming the requirement ("Join this course to see its lessons."); the session is kept |
| Lifecycle refusal (409) | The specific message from the screen's contract (late, graded, used question, not open, last Administrator …); the view reloads the resource before another attempt |
| File too large (413) / unsupported type (400, 415) | "The file is larger than the allowed size." / the field error returned by the API |
| Network failure | Inline rose alert "We couldn't reach CodeMastery. Check your connection and try again." + "Try again" |
| Server problem (5xx, protocol) | "Something went wrong on our side. Try again in a moment." + "Try again". Never show server diagnostics |
| Validation (400) | Field-level messages from the decoded problem detail; otherwise a form-level alert |
| Empty data | Teach the next step (see each screen) |

- Preserve every Live behavior: strict decoders, the ADR014 session lifecycle (restore, renewal, single flight, Web Lock and BroadcastChannel coordination, server sign-out, pending sign-out marker), generation and cancellation checks, no automatic mutation replay, one-use `/profile` return, route heading focus, failed-submit focus, dialog focus lifecycle, Learner-only `/my-courses`, public anonymous catalogue (CT16, FE07, ADR014 §7).
- Keep feature state in its owning feature (CT16-FINAL F1). Shared code stays presentational. Practice-recommendation UI stays in `features/learning` (ADR013 §19.5).
- New repository files (assets, new shared components, a theme hook file, an external first-paint script) are structural changes that need explicit approval under `docs/repository-structure.md`. Prefer the existing files listed below (`theme.ts`, `App.tsx`, `AppHeader.tsx`, `SidebarNav.tsx`, `AuthLayout.tsx`, `LandingPage.tsx`, `index.html`, `PresentationIcon.tsx`). The Theme control is a presentational component exported from the existing `AppHeader.tsx` (like `AccountMenu` and `HeaderIconButton`) and reused by `SidebarNav.tsx`, `AuthLayout.tsx` and the landing header; the preference state lives above the router in `App.tsx`. A separate file for it would need structure approval.

### Acceptance criteria per implemented screen

1. Roles only: no hard-coded colours, radii, shadows or font sizes outside `theme.ts`; no light `color.*` constant in a themed component.
2. Matches its wireframe zones, order and responsive behavior at 360, 768, 1024, 1280 and 1440 px.
3. All states present: loading skeleton, empty, error with recovery, success feedback, forbidden/unavailable where applicable, and each lifecycle refusal its contract defines.
4. Keyboard-only completion of the primary action; visible focus throughout; route focus on `h1`.
5. Text labels on every state; contrast pairs from [Contrast verification](#contrast-verification) in both schemes; 44 px targets.
6. Domain wording from the terminology table; no raw enum values on screen; server reasons verbatim.
7. Renders correctly in light, dark and System (including a live operating-system change) without reload, flash or layout shift; the Theme control is reachable from the screen's shell (except the quiz Focus bar), for visitors and every role.
8. Existing behavior tests still pass; incidental assertions (copy, structure) updated deliberately and listed in the PR.
9. `npm test` and `npm run build` (which includes `npm run typecheck`) run in `frontend/` with their actual results reported.

### Visual QA checklist

- Frame, canvas inset and radius, and canvas reach under the active item, in both schemes.
- Title sizes 40 / 28 / 24 / 18; body 16; no text below 13 px.
- Tiles borderless at 24 px radius with 24 px padding; no nested tiles.
- One primary action per region; Logo Blue only for links, focus, selection and progress.
- Pastel tints only with their semantic job; Unknown and Remaining dashed.
- Path Spine aligned to tile titles; chapters interrupt it.
- Icons from `PresentationIcon` only, same stroke.
- No emoji, no gradient fills (logo artwork and skeleton shimmer aside), no lock for prerequisites, no mastery numbers.
- Dark scheme: canvas visibly lifted from the frame; tiles brighter than canvas; floating surfaces outlined; no pure black, no neon, no light tint on dark; logos and course marks legible; code blocks distinct; charts and map nodes readable.

### UX QA checklist

- Each page answers "where am I, what can I do, what happens next" within one screen.
- Primary action visible without scrolling at 1280 × 720 and 390 × 844.
- Recommendations show type, target and reason; canonical order unchanged.
- Destructive actions confirm with consequences and keep Cancel focused first.
- Errors name the problem and the recovery; retries never duplicate mutations.
- Empty states teach the next step.
- Long titles (80+ characters), long display names and missing names wrap or fall back without breaking layout.
- The theme survives reload, navigation, sign-in and sign-out, and follows another tab; a visitor's choice is still in effect after signing in.
